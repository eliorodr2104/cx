# M4.4: No crash on M0–M4 input; methods look up their receiver first

Status: **Completed** (implemented and verified in this checkout).

Baseline: the pinned checkout recorded in the [M0 record](M0.md).

First of four hardening slices ([M4.4](M4.4.md)–[M4.7](M4.7.md)) that came out
of the 2026-09-23 audit of M0–M4.3. They are grouped by the code they touch, so
each slice is one build-and-test cycle rather than one per bug: a clang rebuild
is slow, and the cost is in regenerating diagnostics and headers, not in the
edits.

This slice closes every **crash** the audit found. It also fixes the method
lookup and method-declaration rules that live in the same Parse/Sema code, and
one blocking bug found while testing it: continuations did not work in C23 at
all (section 13).

Unless noted, each example starts with `#module M` and is compiled with
`clang -x cx`.

## Crashes

**1. Plain C crashed under `-x cx`.**
```c
struct T { int c; }; int g(struct T *p) { return (long)(p)->c; }
```
- Upstream `clang/test/C/C2y/n3254.c` hit the same crash.
- Cause: the Cx method lookup read the type of a `ParenListExpr`, which does
  not have one yet.
- Fix: the lookup now runs after that expression becomes an ordinary
  parenthesized one, as every other member access does.

**2. `var`/`let` with braces or an array.** `let c = {1};`, `var x[] = {1};` and
`let a[2] = 0;` asserted, because the new keyword values overflowed the
diagnostic's `%select`.
- Now `err_auto_init_list_from_c` names `'var'` and `'let'`.
- The C23 array error no longer says `'var'` for a `let`.
- The bit-field error names the keyword actually written.

**3. A method used as a value.** `s->m = 0;`, `&s->m`, and `m = 0;` inside a
sibling method asserted in expression classification. `sizeof(s->m)` and
`__typeof__(s->m)` were silently accepted.
- A method reference is now a bound-member placeholder, as in C++.
- The call that follows resolves it; every other use reaches
  `CheckPlaceholderExpr` and is rejected there with `reference to Cx method
  'm' must be a call`. That covers assignment, `&`, `sizeof`, `typeof`,
  casts, the comma operator and an expression statement.
- The decay-only check it replaces is gone.

**4. A method body inside `typeof`, `sizeof` or `_Alignof`.** CodeGen asserted
"should not emit an unevaluated operand", because the replayed body inherited
the unevaluated context of the expression around the type. The body now runs
in a potentially-evaluated context of its own.

**5. A continuation adding storage through an anonymous member.**
`struct S { union { int b; float c; }; };` reopening a complete `S` asserted,
or silently took `sizeof(struct S)` from 4 to 8. It is now `a continuation of
'S' cannot add a stored field`, like any other field.

Nearby, the valid C11 declaration
`int f4(struct A { struct B { int j; } b; } *);` was mistaken for a continuation.
It is now treated as C's new prototype-scoped type, with C's warning.

**6. A tag declared in a parameter list of an owned function.**
`int f(struct S { int x; } *p) { … }` recursed until the stack overflowed,
because the function's encoding mangled the tag as local to that same
function. Such a tag is now mangled at file scope. A tag in the body cannot
appear in the function's own type, so it stays local. Upstream has the same
bug under `__attribute__((overloadable))`, and this fixes it there too.

**7. A field default reading a local of the enclosing function.** CodeGen hit
`UNREACHABLE` when a method constructed the type. A default is evaluated
wherever the type is constructed, where that local does not exist, so it is
now an error. Not rejected:
- static locals;
- unevaluated operands (`sizeof(k)`);
- a statement expression's own bindings.

**8. `-extract-api` on Cx input** hit `UNREACHABLE`. Cx is reported as `"c"`
until the symbol graph has vocabulary for it.

## Method rules

**9. The receiver wins over file scope.** Before this slice, a global with a
field's name won, silently:
```c
int count;
struct Bag { int count; ~mutating int size() { return count; } void add() { count++; } };
```
- Both methods read and wrote the global, which also slipped past
  `~mutating`. With `<math.h>` included, a field `y1` became the function
  `y1()`.
- Now only the method's own parameters and bindings shadow a member.
- The rule is applied in both places a name resolves: expressions
  (`ActOnIdExpression`), and names at the start of a statement
  (`ClassifyName`, which previously built the global's reference directly).
- A type name keeps its meaning.
- A parameter named `self` is now an error, since it would hide the receiver.

**10. A field and a method of one name** are `duplicate member`, in either
order and across a continuation. Before, the method silently hid the field.

**11. Same parameters and labels, different return type or `~mutating`.**
This reached CodeGen as "definition with same mangled name". It is now
`conflicting types`, because nothing at a call could choose between the two.

**12. Member introducers.**
- `~mutating` on a field is an error.
- A body after several declarators (`int f(), x { … }`) is an error, where it
  used to attach to the first method.
- `~mutating private` is accepted in either order.

## 13. Continuations in C23

C23 accepts a redefinition of a tag whose body is compatible. A Cx
continuation is written exactly that way, and Clang tried the C23 rule first.
So in `-std=c23` and `-std=gnu23` every continuation was read as an
incompatible redefinition:
```text
error: no member named 'a' in 'struct T'
error: type 'struct T' has incompatible definitions
```
[M4b](M4b.md) claimed every C/GNU standard, but no continuation test ran in
C23, so this was not caught.

The rule is now:
- **In an owned file, the continuation wins.** A C23-style identical
  redefinition of an owned type is therefore rejected as a continuation that
  adds a field.
- **An unowned file keeps C's rule**, so existing C23 headers, including
  macro-generated identical definitions, are unchanged.

## Permitted baseline C modes

Every C/GNU standard, as in M0. Only the C23 collision above changes the
meaning of C, and only in an owned file. Everything else only rejects code
that crashed, or constructs that exist only in Cx. The mangling fix in item 6
changes no C symbol: a C function is not mangled.

## C collisions

- In C23, an identical redefinition of an **owned** type is now a
  continuation, so it is rejected (section 13). This is the one change of C
  meaning in this slice. An unowned file is unaffected.
- The receiver-first rule only applies inside a Cx method, which C does not
  have.
- A plain-C `__attribute__((overloadable))` function with a tag in its
  parameter list now mangles instead of overflowing the stack. That upstream
  bug is fixed here, not upstream. No symbol changed, because it never
  compiled before.

## Known limitations

- **An owned C23 identical redefinition is rejected**, rather than recognised
  by comparing it with the primary definition. Recognising it would need a
  structural comparison inside the continuation parser, including nested tags
  and anonymous members. Nothing asks for it yet.
- **Inside a block literal or a nested function in a method**, an unqualified
  name still does not reach the receiver, as before.

## Build and test plan

- **Diagnostics first, once.** Add every new diagnostic a slice needs to
  `DiagnosticSemaKinds.td` in the first edit. Regenerating those tables
  rebuilds most of clang, so doing it once is the saving.
- **Iterate on `.cpp` edits only:** `ninja -C build clang`, then
  `./build/bin/llvm-lit -sv build/tools/clang/test/Cx` (about 2s).
- **Full suite once, at the end:**
  `./build/bin/llvm-lit -s build/tools/clang/test --filter-out 'Index/crash-recovery-modules'`.
  With it excluded, a full run takes about 13 minutes on 8 workers. Without the
  exclusion the run never finishes, because that test deadlocks at exit. The bug is upstream: the fork does not touch any of
  the code involved.
  - `#pragma clang __debug crash` (`Pragma.cpp:1071`) traps inside a stack
    `Timer`, which crash recovery leaves linked into the default `TimerGroup`.
  - The module-build thread crashes first and exits, and its stack is
    unmapped.
  - The parse thread's own pragma `Timer` then runs `TimerGroup::addTimer`,
    which writes through the dangling `FirstTimer` while holding `timerLock`.
    That faults, and crash recovery unwinds past the unlock.
  - At `exit`, the global `OffloadBundlerTimerGroup` destructor waits forever
    for a lock owned by a dead thread.

  Always with parallel runs, never in a sequential run. Only the
  `-fmodules` + nested-crash test reaches it. The clang driver already avoids
  the exit-time half of this (`driver.cpp:461`); libclang does not.
