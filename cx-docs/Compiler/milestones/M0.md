## Source contract

- `clang -x cx file.c` selects Cx explicitly.
- `clangx file.c` defaults ordinary C sources and headers to Cx.
- `clangx -x c file.c` is pure C; plain `clang` never reclassifies `.c` as Cx.
- `-std=` keeps selecting a C standard in Cx mode (`c11`, `gnu23`, …); a C++
  standard is rejected.
- `__CX__` is defined to `1` in Cx mode only. Its final encoding, and a separate
  version macro, remain provisional (see [language-mode](../language-mode.md)).

## Permitted baseline C modes

Every C/GNU standard Clang accepts for `Language::C`. Cx adds no standard matrix of
its own: there is no `cx11`/`cx17`/`cx23`.

## Tests

`clang/test/Cx/`:

- `driver-mode.c`: input-kind selection: explicit `-x cx`, `clangx` default,
  `-x c` override, `-x none` reset, header inputs, assembly not reclassified,
  invalid `--driver-mode=` value.
- `language-mode.c`: macro environment per mode, `-std=` interaction, rejection of
  a C++ standard, cc1 argument round-trip.
- `pch.c`: a Cx PCH is rejected by a C consumer and a C PCH by a Cx consumer.

Verification run on the baseline above: `clang/test` 48909 passed, 30 expectedly
failed, 0 unexpected failures.

## C collisions

None yet: Cx mode currently differs from C only by the `__CX__` macro. That
difference is deliberate and is what differential C tests must classify rather than
normalize away.

## Known limitations

- `__CX__` has no version encoding, and no `__has_feature`-style query exists.
- `clangx` is a working name; the installed spelling is still a naming decision.
- `-cc1 -x cx` is an internal interface, not a stable user API.
- Nothing about `#module`, source ownership, or any Cx syntax is implemented; a Cx
  input is parsed exactly as C today.

## Runnable demonstration

```sh
clangx -dM -E empty.c | grep __CX__     # #define __CX__ 1
clang  -dM -E empty.c | grep __CX__     # nothing
clangx -std=gnu23 -c file.c -o file.o   # ordinary C object
```
