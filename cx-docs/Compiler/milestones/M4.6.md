# M4.6 — Linkage and mangling that link, and don't collide

Status: **Completed** (implemented and verified in this checkout).

Baseline: the pinned checkout recorded in the [M0 record](M0.md).

Third of the hardening slices from the 2026-09-23 audit (see [M4.4](M4.4.md)
for the grouping rationale). Everything here is about **emitted symbols**:
- which linkage a method gets;
- whether two entities can end up with one symbol;
- whether an entity keeps the module it was first declared in;
- which configurations are rejected until the encoding can represent them.

No existing symbol changes.

## Methods

**1. A type with methods defined in its body did not link from a shared
header.** Each method got a strong external definition, so two translation
units including the header gave
`duplicate symbol 'P::_Cx0$Geo$get(P*)'`. A method defined in its type's body
is now `linkonce_odr`, like a C++ member function defined in its class. It is
emitted where it is used and merged at link time. A method implemented in a
continuation stays a strong definition, since that file is its one
implementation. `isCxMethodDefinedInTypeBody` tells the two apart by where the
definition is written.

**2. `typedef struct { … methods … } Anon;` failed** with "anonymous type
given name for linkage purposes by typedef declaration after its linkage was
computed". Two things fixed the linkage too early, before the typedef named
the record:
- The parser handed each method to CodeGen as soon as its body was parsed.
  It now hands it over as C++ hands over a member function defined in its
  class (`HandleInlineFunctionDefinition`). CodeGen defers it past the
  enclosing declaration.
- `-Wmissing-prototypes` asked the method's linkage. It no longer considers
  methods, which are declared by their type, as it does not consider C++
  member functions.

**3. Methods of a type no other translation unit can name had external
linkage.** Two files each with `static struct { … int f() … } a;` gave
`duplicate symbol '$_0::…'`. Methods now get internal linkage when:
- the record is unnamed and no typedef names it for linkage;
- the record is local to a function.

## Encoding

**4. The encoding was ambiguous, and module names were not validated.**
`#module A$B` with `c()` and `#module A` with `B$c()` both gave
`_Z10_Cx0$A$B$cv`, and `-fcx-module=` put `a b`, `1x` or `x.y` straight into
symbols. Two rules now make the encoding injective, with no symbol changing:
- a module name, from `#module` or `-fcx-module=`, is an identifier without
  `$`;
- an argument label cannot contain `$`.

After `_Cx0$`, then, the module runs to the first `$`, and a labels section
is the part after the last `$` of a symbol that ends in `:`. An entity name
may still contain `$`, since it never contains `:`. Length-prefixing every
component was the alternative, and it would have changed every symbol.

**5. `_` as a label collided with "no label".** `language/functions.md` says
`_` spells an unlabeled position (`move(_:mode:)`), but Sema made it a label
called `_`, so `f(int _ a, int mode m)` and `f(int a, int mode m)` had one
symbol. `_` now means unlabeled, so the two are one entity and the second is
a redefinition.

The `:` in the labels section stays. `llvm-cxxfilt` splits on it, but
[M3a](M3a.md) already leaves a Cx-aware demangler to M19.

## Cross-module identity

**6. An entity declared by two modules merged silently.** `#module Alpha` and
`#module Beta` headers each declaring `int get(int)` or `extern int counter`
bound every use to the module whose header was included first. The cause was
worse than the audit said: `cxModuleOfFirstDecl` took the module of any
previous declaration of the name, even another overload with a different
signature.
- A first declaration is now one of the same entity: same type and labels
  for a function, any declaration for a variable.
- A second module declaring it is an error.
- An unowned file may still redeclare it, and a C declaration still keeps
  its C identity.

This closes the case [M4.2](M4.2.md) left open for globals.

**7. `int knr();` in an owned file** reported "'overloadable' function 'knr'
must have a prototype", about an attribute the user never wrote. It is now
`'knr' is declared in a Cx module, so it needs a prototype`, with a fix-it
inserting `void`.

## Configurations rejected until supported

**8. Microsoft ABI targets.** `MicrosoftMangle.cpp` knows neither modules nor
labels, so label overloads collided and owned data kept its C name. `-x cx`
on a `*-windows-msvc` triple is now an error. MinGW, which uses the Itanium
ABI, is unaffected.

**9. `-fmodules`.** `ASTContext::isSameEntity` compares neither labels nor
owner, so importing merged overloads, dropped methods and bound calls to the
wrong module. `-fmodules` in Cx mode is now an error. Teaching `isSameEntity`
labels and owner is the M15 path. PCH and preambles do not merge
declarations and are unaffected.

**10. `-fcx-module=` while building a PCH.** Building a PCH makes a header the
primary file, and build systems pass it the flags of the sources it serves,
so the header's C declarations were renamed into the module. The option no
longer applies to a PCH build. A clangd preamble is the start of the real
primary file and keeps it.

## Permitted baseline C modes

Every C/GNU standard, as in M0. Nothing changes a C symbol:
- method linkage exists only for Cx methods;
- the name rules only restrict Cx spellings;
- the rejected configurations are rejected only with `-x cx`.

`-Wmissing-prototypes` is unchanged for C functions.

## Tests

- **`method-linkage.c`** (with `Inputs/cx-method-header.h`): the linkage of
  - a header method (`linkonce_odr`);
  - a continuation-implemented method (strong);
  - a typedef-named unnamed record (`linkonce_odr`, typedef name in the
    symbol);
  - an unnamed record and a local record (`internal`);
  - an unused method (not emitted).
- **`labels-underscore.c`**: `_` unlabeled at declaration and call; the
  formerly colliding pair is a redefinition; a `$` label is rejected.
- **`module-cross.c`** (with `Inputs/cx-mod-a.h`, `cx-mod-b.h`,
  `cx-mod-b-only.h`): the cross-module errors for a function and a variable,
  and a different overload keeping its own module.
- **`module-names.c`**: invalid `-fcx-module=` and `#module` names, and the
  prototype diagnostic with its fix-it.
- **`unsupported-configurations.c`**: MSVC triples and `-fmodules` rejected;
  MinGW and plain C on MSVC accepted.
- **`module-ownership-pch-flag.c`**: a PCH built with `-fcx-module=` keeps a C
  header's symbols.
- **Updated tests:** `struct-methods.c`, `self-implicit.c` and
  `crash-regressions-codegen.c`, because a method defined in its type's body
  is now emitted after its first use and only when used.

Two-translation-unit programs were also linked by hand: a header type with
methods, and a `static` unnamed record with methods in each file. Both failed
with duplicate symbols before this slice.

## Known limitations

- **Methods of types in unowned files mangle with an empty module**
  (`_Cx0$$…`). Two unrelated `struct Box` types from unowned files of
  different programs linked together would share their method symbols, and
  now merge silently as `linkonce_odr`, as C++ ODR violations do. The rule
  for the unnamed module is
  [G04](../../OPEN-ISSUES.md#g04--source-model-and-visibility).
- **An entity name may still contain `$`.** The encoding stays injective
  because names never contain `:`, but a Cx-aware demangler has to parse from
  both ends. M19.
- **Microsoft ABI and Clang modules** are rejected, not supported.
