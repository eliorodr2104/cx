# M4.6 — Linkage and mangling that link, and don't collide

Status: **Planned** (audited, not implemented).

Baseline: the pinned checkout recorded in the [M0 record](M0.md).

Third of the hardening slices from the 2026-09-23 audit (see [M4.4](M4.4.md)
for the grouping rationale). Everything here changes or constrains **emitted
symbols**, so it is one slice: the Cx mangling tests' `CHECK` lines get
re-baselined once instead of once per fix. Files: `ItaniumMangle.cpp`,
`MicrosoftMangle.cpp`, linkage in `Decl.cpp` / `ASTContext.cpp`, the
first-declaration rules in `SemaCx.cpp`, and a few driver or frontend gates.

## Methods

1. **A struct with a method body in a shared header does not link.** The
   methods get strong external symbols, so including the header in two
   translation units gives
   `duplicate symbol 'P::_Cx0$Geo$get(P*)'`. This is the normal way to write a
   method. A method defined in the type's body should get `linkonce_odr`,
   like a C++ in-class definition (`GetGVALinkageForFunction`). The
   continuation-defined, out-of-line form stays strong.

2. **Methods of an unnamed record get external linkage.** Two translation
   units, each with `static struct { … int f() … } a;`, give
   `duplicate symbol '$_0::_Cx0$M$f($_0*)'`. Give them internal linkage.
   - Related: `typedef struct { …; void inc() {…} } Anon;`, a common C idiom,
     fails with "unsupported: anonymous type given name for linkage purposes".
     The typedef name should be the linkage name, as in C++.

3. **Methods in unowned files mangle with an empty module**
   (`_ZN3Box12_Cx0$$set…`), so two unrelated `struct Box` types in two unowned
   programs' files collide at link time. Decide per
   [G04](../../OPEN-ISSUES.md#g04--source-model-and-visibility) (unnamed module), and at least document it.

## Encoding

4. **`$` is an unescaped separator, so the encoding is ambiguous.**
   `#module A$B` + `int c(void)` and `#module A` + `int B$c(void)` both give
   `_Z10_Cx0$A$B$cv`. `-fcx-module=` is not validated at all: `"a b"`, `1x`,
   `x.y` and `A$B` all go straight into symbols. To fix it:
   - Length-prefix each component in `mangleCxName` (`ItaniumMangle.cpp` ~1784)
     so the encoding is injective.
   - Validate module names as identifiers in both `#module` and `-fcx-module=`.
   - While changing the encoding, decide whether `:` in labels stays.
     `llvm-cxxfilt` splits on it, and M3a already defers a Cx-aware demangler
     to M19.

5. **`_` as a label collides with "no label".** The docs say `_` means
   unlabeled, but Sema treats it as a real label (`f(1)` gives `missing
   argument label '_:'`). Then `void f(int _ a, int mode m)` and
   `void f(int a, int mode m)` both give `_Z16_Cx0$M$f$_:mode:ii`. Make `_` mean
   unlabeled in Sema (preferred, since it matches the docs), or encode unlabeled
   positions distinctly.

## Cross-module identity

6. **Same-named declarations from two modules merge silently, and include
   order picks the symbol.** `ma.h` (`#module A`) and `mb.h` (`#module B`) each
   declare `void f(int x v); int g(int);` or `extern int counter;`. With both
   included, calls bind to `_Cx0$A$…`; with only `mb.h`, to `_Cx0$B$…`. M4.2
   claims the cross-module global collision is closed; this case is not.
   `cxModuleOfFirstDecl` (`SemaCx.cpp:45`) takes the first owner. Diagnose a
   redeclaration whose owner differs from the first declaration's.

7. **`int knr();` in an owned file** gives "'overloadable' function 'knr' must
   have a prototype", about an attribute the user never wrote. Give a Cx
   diagnostic (an owned function needs a prototype), or give an unprototyped
   declaration C linkage.

## Targets and build modes, reject until supported

8. **The Microsoft mangler ignores Cx linkage.** On
   `-target aarch64-pc-windows-msvc`, two label overloads give "definition with
   same mangled name '?move@@$$J0YAXH@Z'". A module-owned `counter` stays
   `@counter`, and modules A and B produce the same `?get@@…`. Reject `-x cx`
   on MSVC-ABI targets in the driver and frontend, with a test, until
   `MicrosoftMangle.cpp` learns modules and labels.

9. **`-fmodules` breaks Cx semantics:**
   - methods disappear from imported records (`LookupCxMethod`, `SemaCx.cpp`
     ~545, returns null);
   - overloads that differ only by label merge;
   - calls bind to the wrong module.

   `ASTContext::isSameEntity` (`ASTContext.cpp` ~7797–7858) compares neither
   `CxArgumentLabelAttr` nor the `CxLinkage` module. Reject `-fmodules` in Cx
   mode for now; teaching `isSameEntity` labels and owner is the M15 path.
   PCH is unaffected, since it does not merge.

10. **`-fcx-module=` also applies to the header when building a PCH**
    (`Preprocessor.cpp`, `EnterMainSourceFile`). The PCH gives
    `_Z16_Cx0$Boxes$boxedi`; a textual include gives `@boxed`. Build systems
    reuse TU flags for the PCH build, so C declarations in a prefix header get
    renamed. Skip it when the main file is a PCH or prefix header, or diagnose
    it.
