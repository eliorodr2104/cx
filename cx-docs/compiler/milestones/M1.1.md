# M1.1: Separate `auto`, `__auto_type`, `var` and `let` in the AST

Status: **Completed** (implemented and verified in this checkout).

Intermediate milestone between [M1](M1.md) and M2. It changes no accepted source
semantics; it makes the compiler represent four placeholder specifiers as four
distinct things instead of folding the Cx pair onto the GNU one.

## Why

M1 shipped `var` and `let` by reusing `AutoTypeKeyword::GNUAutoType`, the
placeholder that backs `__auto_type`. The deduction behavior was right, but the
AST could no longer say which specifier the developer wrote, so diagnostics had to
guess from the language mode. In Cx mode a declaration written `__auto_type`
reported itself as `var`, and `let` had no spelling of its own at all.

`auto`, `__auto_type`, `var` and `let` are four different declarations. C `auto`
is a storage class before C23 and a C23 placeholder after it; `__auto_type` is a
GNU extension; `var` and `let` are Cx declarations with their own mutability
rule. Sharing one representation was an implementation shortcut, not a language
statement, and the roadmap forbids calling a feature complete by special-casing
its only example.

## Source contract

Unchanged from M1. What changes is what the compiler reports:

| Written | Reported as | Independent deduction in a group |
| --- | --- | --- |
| `auto` | `auto` | no |
| `__auto_type` | `__auto_type` | no |
| `var` | `var` | yes |
| `let` | `let` | yes |

C `auto` and `__auto_type` keep their selected-dialect meaning inside Cx mode.
They are not spellings of `var`, and a Cx rule never reaches them: in Cx mode
`__auto_type a = 1, b = 2.0;` is still rejected, exactly as in C.

An undeduced `let` placeholder prints as `let`, not `const let`: the specifier
already carries the const it introduces.

## Implementation

| Area | Change |
| --- | --- |
| `clang/include/clang/AST/TypeBase.h` | `AutoTypeKeyword::CxVar` and `CxLet`; `AutoTypeBits.Keyword` widened to 3 bits; `isCxVar`, `isCxLet`, `isCxInference`, `isDeducedFromInitializerOnly` |
| `clang/include/clang/Sema/DeclSpec.h` | `DeclSpec::CxInferenceKind` records which specifier was written |
| `clang/lib/Sema/SemaType.cpp` | `TST_auto_type` builds the matching keyword; `IsCXXAutoType` and the not-allowed diagnostic use the new predicate and spellings |
| `clang/lib/Sema/SemaDecl.cpp` | the group deduction check reads the keyword off the type, so `BuildDeclaratorGroup` loses its extra parameter |
| `clang/lib/Sema/SemaExpr.cpp`, `clang/lib/AST/ASTContext.cpp` | assignment and type merging use `isDeducedFromInitializerOnly()` |
| `clang/lib/AST/TypePrinter.cpp` | prints `var` / `let`; drops the redundant const on an undeduced `let` |
| `clang/lib/AST/JSONNodeDumper.cpp` | `typeKeyword` reports `var` / `let` |
| `clang/lib/AST/ItaniumMangle.cpp`, `MicrosoftMangle.cpp` | the "never mangled" assertions cover the Cx specifiers |
| `clang/include/clang/AST/PrettyPrinter.h` | the `CxInference` policy bit added by M1 is removed; the spelling now lives in the type |

`isDeducedFromInitializerOnly()` identifies a C placeholder deduced from its
initializer without C++ `auto` rules. `isGNUAutoType()` now means only the literal
`__auto_type` spelling. Every site that previously
asked `isGNUAutoType()` for behavior was moved to the predicate; the two sites
that ask about spelling were left alone.

## Tests

`clang/test/Cx/var-let-diags.c` gains the four-spelling cases: `var`, `let` and
`__auto_type` each rejected in a function prototype under their own name, and an
`__auto_type` group still rejected for inconsistent deduction inside Cx mode.

Verification run on this checkout: `clang/test` 48914 passed, 30 expectedly
failed, 0 unexpected failures.

## Known limitations

- `let` is still implemented as a `CxLet` placeholder plus a `const` type
  qualifier from the declarator, rather than a placeholder that produces a
  const type by itself. This is invisible in source and in diagnostics, but a
  future `~mutating` or field-level rule (M4) may want the const to come from
  the specifier.
- Serialization stores the keyword as an enum value, so a PCH written before
  this change and read after it would misread the keyword. Cx has no stable
  artifact format yet (G09), and PCH validation already rejects cross-mode
  reuse, so nothing versioned depends on this.
