# M6.1: `.case` in aggregate and tuple elements

Status: **Completed** (implemented and verified in this checkout).

Baseline: the pinned checkout recorded in the [M0 record](M0.md).

Closes roadmap row M6 after [M6e](M6e.md). [M6b](M6b.md) gave `.case` its enum
from the expected type at the start of an expression; this milestone brings the
expected type into the elements of braced initializers and tuple literals.

```c
struct Pixel { int x; Color c; };
struct Frame { struct Pixel p[2]; Token t; Permission perm; };

struct Pixel a = { 1, .green }
struct Pixel b = { .c = .blue, .x = 2 }
struct Frame f = { { { 1, .red }, { .c = .green } }, .integer(4), [.read] }
(int, Color) t = (1, .green)
return (struct Pixel){ 5, .blue }
```

## The rule

A braced initializer knows the type it initializes: the declared type, a
compound literal's type, or, for a nested list, its element's type. Each of its
elements then takes:

- **positionally**, an array's element type, a struct's or tuple's next field
  (unnamed bit-fields skipped), a union's first field, or the scalar itself for
  `Color c = { .red }`;
- **after a designator** `.f.g[2] =`, the type the chain reaches; positions
  then go on with the field after a designated one, as in C.

A tuple literal whose destination is known (an initializer, `=`, an argument
whose parameters agree, `return`, or an enclosing tuple or braced element)
gives each element that element's type.

The element's type reaches a `.case`, a payload construction, an option set
literal, a nested braced list and a nested tuple literal.

The expected type is computed while parsing, from the destination, instead of
resolving the case afterwards: every context that reaches it already knows its
type. The roadmap had planned a deferred resolution; it proved unnecessary.

## Disambiguation

- In braces, `.name` and `[...]` are designators only when their chain reaches
  `=`, so `{ .red }` and `{ [.read] }` are elements while `{ .x = 1 }` and
  `{ [2] = 1 }` stay C.
- An unlabelled `(a, b)` in braces is a tuple when its element has a tuple type,
  which no C type is; M6a's limitation on `{ (1, 2), 3 }` is gone for tuple
  fields.

## Brace elision

C lets a nested aggregate lose its braces: in `{ 1, .red }` for
`struct { struct { int x, y; } p; Color c; }`, `.red` initializes `p.y`. The
element is typed as the member it would initialize without elision, `c`, so
`.red` is a `Color` given to an `int`, which is an error. A Cx case converts to
nothing else, so a wrong guess is always a diagnostic, never silent code.

## Permitted baseline C modes

Every C/GNU standard, as in M0.

## Implementation

| Area | Change |
| --- | --- |
| `clang/lib/Parse/ParseInit.cpp`, `Parser.h` | the list's type and each element's (`prepareCxElement`); designators reach `=` for `[` too |

## Evidence

- The full Clang lit suite passes, with the known deadlocking
  `Index/crash-recovery-modules.m` filtered out.
- The IR of every enum and tuple test file is identical to the IR of its
  `-ast-print` output.

## Tests

- **`enums-contexts.c`**, as IR and after `-ast-print`: positional and
  designated struct fields, positions after a designator, nested lists and
  arrays of structs, a payload enum field, an option set field, a union, a
  scalar in braces, compound literals, tuple literals in an initializer, `=`,
  an argument and `return`, a nested tuple, and a tuple field in braces.
- **`enums-raw-errors.c`**: brace elision onto a field of another type.

## Known limitations

- **Brace elision** guesses the member without elision; a mismatch is an error.
- ~~**Payload arguments** still have no expected type: `.wrap(.red)` needs
  `.wrap(Color.red)`.~~ Closed by [M6.2](M6.2.md).
- **`.case == value`** still needs the enum on the left.
