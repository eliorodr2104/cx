# M5.1: Line breaks that C cannot continue

Status: **Completed** (implemented and verified in this checkout).

Baseline: the pinned checkout recorded in the [M0 record](M0.md).

A hardening pass over [M5b](M5b.md), which let C read every line break it could
read as a continuation. A line beginning with `(`, `[`, `*`, `&`, `-` or `+` then
continued the one before even where the result was an error, so `p->init(5)`
followed by `(p + 1)->init(6)`, or `x = f()` followed by `*p = 3`, needed a `;`.

```c
p->init(5)
(p + 1)->init(6)     // two statements: init(5) is void and cannot be called
x = f()
*p = 3               // two statements: (f() * p) = 3 is never C
total = a
  - b                // one expression, as in C
effect
(4)                  // one call, as in C
```

## The rule

The specification asks for *continuation validity*: a line break ends a
statement where C cannot validly continue it. M5b tested that syntactically;
this pass also tests it by type, at the start of a line, in Cx:

| Line begins with | Continues when | Otherwise |
| --- | --- | --- |
| `(` | the expression before is a function, function pointer or block | new statement |
| `[` | the expression before is a pointer, array, integer or vector | new statement |
| `++`, `--` and then a name, number, character or `(` | never (`a++ b` is not C) | new statement |
| `*`, `&`, `-`, `+` | the line does not assign at its top level | new statement |

The result of a binary `*`, `&`, `-` or `+` is never assignable in C, so a line
such as `*p = 3`, `*p++ = v` or `-x += 1` could only be an error as a
continuation. `x = a\n-b` stays `x = a - b`, as the specification requires for
arithmetic across lines.

## Compared with Swift and Kotlin

Swift never continues with `(` or `[` at the start of a line and reads operators
by their spacing; Kotlin continues only with `.`, `?.`, `&&`, `||` and `?:`. Cx
cannot copy either, because `foo\n(bar);` and `x = a\n  -b;` are valid C, but
it reaches their result wherever C gives the tokens no meaning. The two
differences left are a function alone on a line before `(...)`, and `-b` alone
as a statement, neither of which does anything.

## Permitted baseline C modes

Every C/GNU standard, as in M0. No valid C changes meaning: each new boundary is
a place where the continuation is a type or syntax error in C.

## Implementation

| Area | Change |
| --- | --- |
| `clang/lib/Parse/ParseExpr.cpp`, `Parser.h` | `isCxLineBoundaryBeforeSuffix` in the postfix loop; `isCxLineBoundaryBeforeOperator` in the binary loop; a payload's `(` must be on its case's line |

## Evidence

- The full Clang lit suite passes, with the known deadlocking
  `Index/crash-recovery-modules.m` filtered out.
- `implicit-semicolons.c` keeps its C continuations: `effect\n(v)`,
  `v = v\n - 1` and `return\n compute()`.

## Tests

- **`implicit-semicolons-lines.c`**, with `-Wcx-implicit-semicolon`, as IR and
  after `-ast-print`: a `void` call before `(`, a function before `(`, `*p = 3`
  and `*q++ = 5`, arithmetic across lines, `++n`, and a pointer before `[`.
- **`deinit.c`** writes `p->init(5)` before `(p + 1)->init(6)` and `h->deinit()`
  before `(p + 1)->deinit()` without separators.

## Known limitations

- **`x = a\n-b`** is still `x = a - b`, and **`f\n(x)`** with a function `f` is
  still a call, as C requires. A `;` separates them.
